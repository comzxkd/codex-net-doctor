# 设计依据

这份文档记录「为什么这么写」，方便以后自己或别人接手时不用重新推导一遍。

## 一、端点从哪来

工具要测的域名不能靠猜。每一个都核对过上游。

**来源一：`openai/codex` 仓库源码**

`codex-rs/codex-api/src/lib.rs`：

```rust
/// Path of the Responses endpoint, relative to a provider's base URL.
pub const RESPONSES_PATH: &str = "/responses";
```

这是相对 provider base URL 的路径。也就是说最终地址 = base URL + `/responses`。

**来源二：两种认证模式各自的 base URL**

- 账号登录模式：`https://chatgpt.com/backend-api/codex`
- API Key 模式：`https://api.openai.com/v1`

合起来就是：

| 模式 | 最终地址 |
|---|---|
| 账号登录 | `https://chatgpt.com/backend-api/codex/responses` |
| API Key | `https://api.openai.com/v1/responses` |

**来源三：登录链路**

`https://auth.openai.com/oauth/token` 负责换 token，`auth.openai.com/api/accounts` 负责账号接口。登录失败基本都卡在这一段。

**一个容易漏掉的点**：`codex-rs/core/src/client.rs` 里 Codex 会用 WebSocket 复用连接（`ResponsesWebsocketClient`，注释里提到 `response.create` 预热）。WebSocket 的链路特征和普通 HTTPS 不同，很多分流规则只写了 HTTP 规则，漏了 WS 规则。这解释了一类「能登录、能聊天、但 Codex 跑一阵就断」的症状。

这一条目前**没有**实现成检查项，记在这里待办。

## 二、判定为什么要看状态码而不是国家码

`chatgpt.com/cdn-cgi/trace` 返回的 `loc=` 是 Cloudflare 边缘对这颗粒 IP 的国家判定。它好用、免费、一眼能看懂，但它不是 OpenAI 自己的判定。

Cloudflare 和 OpenAI 用的是不同的 IP 地理库，边界情况会不一致。所以：

- **国家码** → 展示给用户看，标成「旁证」
- **接口返回码** → 作为结论依据

具体做法：对 `api.openai.com/v1/models` 发一个不带 token 的 GET。

- `401` → 出口地区没问题，只是没鉴权
- `403` + body 含 `unsupported_country` → 地区被拒
- `403` 但 body 不含该字样 → 只是没登录，不是地区问题

第三点是关键。很多排查工具看到 403 就报「地区不支持」，误报率很高。

## 三、为什么不模拟「代理」和「直连」两条路

最初的设计是想分别测「走代理」和「直连」，用出口差异判断分流有没有生效。

实际上跑不通，原因：

1. 用户可能开着 TUN。TUN 在虚拟网卡层接管所有流量，代码层面怎么绕都绕不出去，所谓「直连」测的还是同一条路。
2. 绕过 TUN 需要绑定物理网卡源地址或改路由表，属于会动系统状态的操作，跟「只读诊断」的原则冲突。

所以改为：**只测用户实际会走的那条路**。这也更贴近问题本身——用户要的不是「理论上两条路有什么区别」，而是「我现在这个配置能不能用」。

## 四、地址归类为什么不用 `ipaddress` 模块

`ipaddress` 是标准库，本来是最自然的选择。改成手工算整数有三个原因：

1. 需求极简，只需要判断「这个地址在不在这个网段」。手算 `(value & mask) == network` 一行就够。
2. `ipaddress` 的 `__contains__` 依赖内部对象状态，出问题时不好查。手算的中间值可以直接打出来核对。
3. 实测发现某些执行环境会改写源文件里的 IP 字面量，`ipaddress` 会把这错误一路吞下去，手算至少每一步都能看见。

对应地，`tests/test_probe.py` 里所有地址都用 `ip(a, b, c, d)` 现场拼，不写进源码。

## 五、WebSocket 为什么值得单独测

`codex-rs/core/src/client.rs` 里，Codex 会开一个 WebSocket 连接缓存起来重复用（`ResponsesWebsocketClient`，注释里提到预热的 `response.create`）。这是为了省掉每次对话的握手开销。

问题在于分流规则。Clash、sing-box 这类工具的规则里，「域名走代理」和「WebSocket 走代理」是两回事：只写 `DOMAIN-SUFFIX,chatgpt.com,PROXY` 通常够用，但一旦规则里带了 `network` 字段而只写了 `tcp`，或者用了针对 HTTP 的匹配条件，WebSocket 就会漏。

症状很特殊：能登录、能对话，但用一阵子就断。用普通 HTTPS 探测完全看不出来。

### 怎么判读

WebSocket 没有「200 成功」这回事，没凭据也不可能真的升级成功，所以判据不能是「有没有 101」：

| 回什么 | 说明 |
|---|---|
| `101` 且 `Sec-WebSocket-Accept` 对得上 | 真的升级成功了 |
| `401` / `403` 且响应头里有 `cf-ray` | 走到了 Cloudflare，只是没凭据。链路是通的 |
| `404` | 路径可能改过。**不归因给用户网络**，标为「不可靠」 |
| 超时 / 502 / 不带 `cf-ray` 的错误页 | WebSocket 这条路没通 |

第三行是关键。如果哪天 OpenAI 换了路径，工具不应该反过来污赖用户的代理坏了，而应该说「我这条探测可能过时了」。

### 路径怎么来的

`codex-rs/codex-api/src/lib.rs` 里 `RESPONSES_PATH = "/responses"` 是相对 provider base URL 的。WS 沿用的是同一个 base 和同一个 path，只是换了 scheme。所以探测地址是 `wss://chatgpt.com/backend-api/codex/responses`，对应到我们这里是 `host=chatgpt.com, path=/backend-api/codex/responses`。

这个推导没法完全从源码一眼确认（URL 拼接在 provider 层），所以代码里保留了 404 的降级分支：如果实测返回 404，说明我推错了，工具会自己报「端点可能改过」而不是乱下结论。

## 六、稳定性怎么算

一个地址连一遍只能说明「此刻能不能用」。要回答「稳不稳定」必须多轮。

做法：同一批地址连着跑 N 轮（默认 3），第一轮取完整细节（四段耗时、响应头、响应体），后两轮只记「通/不通」和耗时。

为什么不用 ping 或 TCP 握手代替：这两样都只能证明网络层可达。TLS 能不能谈成、HTTP 能不能拿到状态码，是两回事。一个地址可能 TCP 每轮都通、TLS 时而失败，这种恰恰是「能连但用不了」的典型。

局限：3 轮的样本量很小，说不出「成功率 67%」这种话，只能说「3 轮里坏了几轮」。措辞上就按这个尺度写，不夸大。

代价是检测时间从十几秒涨到大约半分钟。所以留了 `--rounds` 开关。

## 七、总结为什么只给一条问题

用户要的是四句话：通不通、稳不稳、问题在哪、怎么解决。而不是一张表格自己拼。

前两句能直接算出来。后两句的取舍是：**只拿最要紧的那一条**，剩下的放进下方的「其余问题」。

理由：同时告诉用户五件事等于什么都没说。先让他动一件事，动完了再跑一次看下一件。

选哪一条不能靠顺序。同级别几条共存时，插入顺序是随机的，会让同一个网络状况两次跑出不同结论。所以按影响加权：地区限制 > 断在某一环 > WebSocket 专项，同类里命中的检查项越多越靠前。

## 八、提示词为什么要写成那个样子

工具能定位到「哪一段断了」，但真正要改的是代理软件的分流规则，那得看用户的配置文件。让用户自己在对话里一段段描述现状，成本很高。所以直接给一段能复制的提示词。

三条原则：

**一、自带上下文。** 对方的 agent 没有我们这边的任何信息。结论、具体断点、原始错误、代理设置、TUN 状态、出口地址、Codex 会连哪些地址，全得写进去，否则它要重新问你一遍。

**二、不写死步骤。** 只说要查什么、判断标准是什么，不写「第一步执行 X」。真正的排查得按现场情况走，写死了会反过来误导。比如「断在连接」那一段，只说要去对比走代理和不走代理两种结果，不告诉它用哪条命令。

**三、结尾必须收住。** 默认只读排查，改配置前先把要改的内容贴给用户看。网络配置改错了比不改更难排查，这个决定不该交给 agent。

提示词的类型是在生成结论时就标好的（`kind` 和 `stage` 字段），不靠标题字符串去猜。猜字符串太脆，改一个字就失效。

## 九、当前局限

- **只覆盖 Codex/GPT**。Claude、Gemini 的域名表还没加，加进去成本不高。
- **WebSocket 的路径是推导出来的**，不是从源码逐字读到的。已加 404 降级保护，但仍属推定。
- **稳定性采样 5 轮**。能发现「时通时断」，但不足以给出成功率数字；页面上写的是「几轮里坏了几轮」，不是百分比。
- **提示词是模板生成的**，不是模型现写的。好处是可审计、不花钱、不联网；代价是遇到模板没覆盖的情况只能给一段通用建议。
- **TUN 判定是推测**。只有两条线索（fake-ip 地址、出口网卡地址），两条都不命中时无法下结论。
- **没做 DNS 泄漏检测**。要判断解析请求实际发给了谁，需要抓包或读代理软件日志，超出「纯标准库只读」的范围。
- **Windows 之外的平台没验证过**。系统代理读注册表那段在 macOS/Linux 上会直接跳过，其余逻辑是跨平台的。

## 十、明确不做的事

不自动修改用户的代理配置、分流规则、hosts、环境变量。

理由：这个工具的输入是「不确定的配置」，输出如果也是「改配置」，一旦判断错了，用户会陷入更难排查的境地。诊断和修复分开，修复交给用户自己做决定。
